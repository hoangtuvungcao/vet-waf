Installation

Quick start

Get Vet-WAF built, configured, and passing live traffic. Vet-WAF runs inside the Linux TCP/IP stack, so it needs a patched kernel — plan for one reboot.

1. Requirements

Before you begin, confirm the host meets all of the following. Vet-WAF is a kernel module: a mismatch here fails the build rather than degrading gracefully.

RequirementDetails
KernelLinux 6.12.12 with the Vet-WAF patch applied (see Kernel patching)
Architecturex86-64 with AVX2. Vet-WAF uses AVX2 for string and hash routines
Privilegesroot, to load kernel modules and bind privileged ports
Build toolsgcc, make, and the matching kernel headers/source tree
Memory2 GB minimum; more if you enable the in-RAM cache

Verify AVX2 support before building: grep -o avx2 /proc/cpuinfo | head -1. No output means this CPU cannot run Vet-WAF.

2. Build from source

Clone the repository and build the kernel modules and user-space tools. The build links against the running kernel's headers, so patch and boot the kernel first.

bash 
git clone https://github.com/hoangtuvungcao/vet-waf.git
cd vet-waf

# Build every module: fw, tls, db, lib, regex
make

# Optional: run the in-kernel unit tests
make test

3. Configure

Vet-WAF reads etc/vet_waf.conf from the source tree by default, overridable with the TFW_CFG_PATH environment variable. The shipped template is secure by default: the only line you must change is the backend.

vet_waf.conf 
listen 80;

block_action attack drop;
block_action error  reply;

frang_limits {
    ip_block 600;
    request_rate               100;
    request_burst               30;
    tcp_connection_rate         50;
    concurrent_tcp_connections 100;
    client_header_timeout       10;
    http_strict_host_checking true;
}

srv_group primary {
    server 127.0.0.1:8080;   # <-- your application
}

vhost default {
    proxy_pass primary;
}

http_chain { -> default; }

Every limit above is enforced per client IP, not globally, so one attacker cannot consume the budget belonging to real users. See Frang rules for the full set.

4. Start Vet-WAF

The control script loads the modules in dependency order and pushes your configuration into the kernel.

bash 
# Load modules and start
sudo ./scripts/vet_waf.sh --start

# Apply config changes without dropping connections
sudo ./scripts/vet_waf.sh --reload

# Stop and unload
sudo ./scripts/vet_waf.sh --stop

5. Verify it is working

Three independent checks: the module state, the traffic counters, and a real request.

bash 
# 1. Is the engine running?
sudo sysctl net.vet_waf.state       # expects: start

# 2. Live counters (requests, responses, cache, errors)
cat /proc/vet_waf/perfstat

# 3. Does a real request get proxied?
curl -I -H 'Host: example.com' http://127.0.0.1/

Always send a Host header when testing. The default configuration enables http_strict_host_checking, so a request without a valid host is rejected by design — that is the WAF working, not a failure.
