Anti-DDoS

Frang rules

Frang is the rule engine that turns Vet-WAF into a WAF. Every limit is per client IP, and every one of them is off by default until you set it.

How Frang works

Frang is Vet-WAF’s per-client enforcement engine. Every limit below is counted per client IP, not globally, so a single attacker cannot consume the budget that belongs to your real users.

Limits live in a frang_limits block. Place it at the top level for global defaults, or inside a vhost to override them for one site. A limit left at its default of 0 is disabled — nothing is enforced until you set a number.

vet_waf.conf 
frang_limits {          # global defaults
    request_rate 100;
}

vhost api.example.com {
    frang_limits {      # stricter, for this vhost only
        request_rate 20;
        http_methods get post;
    }
    proxy_pass primary;
}

The single most important directive is ip_block. Without it a flooder is merely throttled request by request; with it the offending IP is banned outright on its first violation. That is the difference between a rate limit and an actual mitigation.

Request and connection floods

A volumetric L7 attack either sends too many requests or opens too many connections. Rates are measured per second; a burst is the ceiling within a single 1/8-second sub-interval, which catches short spikes that a per-second average would smooth over.

DirectiveDefaultWhat it stops
ip_blockoffBans the IP for N seconds when any limit here is tripped
request_rate0Sustained requests/second per client
request_burst0Short request spikes inside one second
tcp_connection_rate0How fast new TCP connections may be opened
tcp_connection_burst0Sudden bursts of new connections
concurrent_tcp_connections1000Socket exhaustion — too many sockets held open at once
tls_connection_rate0Handshake floods, which cost the server far more CPU than the client
tls_connection_burst0Bursts of TLS handshakes
tls_incomplete_connection_rate0Handshakes deliberately started and never finished

Tune these to your real traffic before deploying. A normal browser loading one page with its assets produces a burst of a few dozen requests and then goes quiet — but users behind a large corporate NAT all share one IP, so set ip_block low or omit it in that case.

Slowloris and slow-drip attacks

Slowloris keeps thousands of connections alive by trickling a request a few bytes at a time. It exhausts your connection table without ever generating the volume a rate limit would notice, so it needs its own defences.

  • client_header_timeout / client_body_timeout — the whole request head or body must arrive within N seconds, however slowly it is sent.
  • http_header_chunk_cnt / http_body_chunk_cnt — the head or body may not be split across more than N network chunks. This catches the byte-at-a-time drip directly, even if it stays inside the timeout.
vet_waf.conf 
frang_limits {
    client_header_timeout   10;
    client_body_timeout     30;
    http_header_chunk_cnt   10;
    http_body_chunk_cnt    256;
}

Raise the two body values if you accept large uploads over slow mobile links. Leave the two header values tight — no legitimate client needs more than a second or two to send its request headers.

Malformed and oversized requests

These bound every structural part of a request. Oversized-header attacks and HTTP/2 HPACK bombs both die here, and the same caps protect the parser itself from pathological input.

DirectiveDefaultPurpose
http_header_cnt50Maximum number of header fields
http_hdr_len0Maximum length of any single header, in bytes
http_uri_len0Maximum request-URI length
http_body_len1073741824Maximum request body. Every byte is memory an attacker can make you hold
http_strict_host_checkingtrueRejects an absent, duplicated, or contradictory Host header — closes cache poisoning, host confusion, and request smuggling
http_methodsallAllow-list of methods, e.g. get head post
http_method_override_allowedfalseKeeps X-HTTP-Method-Override from smuggling a DELETE past a filter that only sees a POST
http_trailer_split_allowedfalseRejects trailers split across continuation frames — a smuggling vector with no legitimate use
http_ct_required / http_ct_valsfalseRequire a Content-Type, optionally from an allow-list

One further hardening step lives at the top level, outside the frang_limits block: http_uri_brange restricts which byte values may appear in a URI at all, rejecting anything else before parsing. It blocks entire injection families at the door but will break sites that use non-ASCII URLs, so test it first.

Ejecting scanners and brute force

A client that racks up error responses is enumerating your site rather than browsing it. http_resp_code_block watches the responses you send and ejects the client once it collects too many. In practice this is the single most effective rule against automated scanners and credential brute-forcing.

vet_waf.conf 
# Syntax: http_resp_code_block <code>... <limit> <seconds>;
#   the last two numbers are the limit and the time frame;
#   everything before them is the list of HTTP codes to count.

frang_limits {
    ip_block 600;
    http_resp_code_block 400 403 404 405 413 429 500 25 15;
}

Read that as: if a client collects 25 responses carrying any of those codes within 15 seconds, treat it as an attack. Combined with ip_block 600 above it, the scanner is banned for ten minutes instead of being allowed to keep probing.

Count 404 with care on a site that legitimately serves missing images or favicons — a single broken page template can trip 25 of them for an innocent visitor. Verify against your own access logs before enabling it in production.

Verifying that a rule fired

Frang logs every block with the reason and the client address, and the counters are exposed through procfs. Watch both while you test.

bash 
# Live kernel log: every Frang decision, with the reason
sudo dmesg -w | grep -i frang

# Aggregate counters
cat /proc/vet_waf/perfstat

# Trip request_rate on purpose from another host
for i in $(seq 1 500); do curl -s -o /dev/null \
    -H 'Host: example.com' http://TARGET/ & done; wait

Test from a second machine, never from the host itself. With block_action attack drop the reply is dropped silently, so a tripped limit looks exactly like a network timeout on the client side — that silence is the intended behaviour, not a fault.
