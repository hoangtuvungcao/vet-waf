Troubleshooting

Vet-WAF runs in kernel space, so the answer is almost always in dmesg. This page maps each common symptom to its cause.

Start here

Vet-WAF runs in kernel space, so its diagnostics are in the kernel log rather than an application log file. These four commands answer most questions before you change anything.

bash 
uname -r                          # must be the patched 6.12.12
lsmod | grep -E 'tempesta|vet'    # are the modules loaded?
sudo sysctl net.vet_waf.state     # expects: start
sudo dmesg | tail -50             # the actual error, always

Read dmesg first, every time. The configuration parser names the exact directive it could not accept, and Frang logs every block with its reason and the client address. Guessing from the client side wastes far more time.

It will not start

SymptomCause and fix
insmod fails with invalid module formatThe modules were built against a different kernel than the one running. Confirm uname -r is 6.12.12, then make clean && make.
Unknown symbol in dmesgThe running kernel is unpatched or only partially patched. Reapply linux-6.12.12.patch to a clean tree and rebuild — a half-applied patch loads and then misbehaves.
Illegal instruction on loadThe CPU lacks AVX2, which Vet-WAF requires for its string and hash routines. Check with grep -o avx2 /proc/cpuinfo | head -1.
Stops immediately, config error in dmesgThe parser rejected a directive and names it. The usual culprits are a missing semicolon and a global tls_certificate alongside a named vhost, which are mutually exclusive.
Kernel panic at startupAlmost always a health name in a srv_group that matches no health_check block. The name is not validated at parse time. Make the two names identical and define the block first.

Real users are being blocked

A secure-by-default configuration will reject some real traffic until it is tuned to your site. Work through these in order — the first two explain most reports.

  • Requests fail without a Host header. http_strict_host_checking is on by default and rejects an absent, duplicated, or contradictory Host. That is the WAF working. Send -H 'Host: yoursite' when testing with curl.
  • PUT, DELETE or OPTIONS return an error. http_methods is an allow-list. Add the methods your API genuinely uses, and no more.
  • Uploads fail above a certain size. Raise http_body_len to your largest legitimate upload — but only that far, since every byte is memory an attacker can make you hold.
  • A whole office goes offline at once. They share one public IP behind NAT, so they share one Frang budget. Raise request_rate and concurrent_tcp_connections, and lower or remove ip_block.
  • Visitors are banned after browsing normally. http_resp_code_block counts 404s. One broken page template that requests missing assets can trip the limit for an innocent visitor.

With block_action attack drop the reply is dropped silently, so a blocked client sees a network timeout rather than an error page. Do not diagnose from the client side — dmesg | grep -i frang names the rule and the IP.

Backend errors

StatusMeaningWhat to check
502Vet-WAF cannot reach the origin at allTest the origin directly from the edge node: curl -v http://ORIGIN:80/. Then check the firewall between them.
504The origin accepted the connection but answered too slowlyRaise server_forward_timeout, or fix the slow origin. Under load, also raise server_queue_size.
503No healthy server left in the groupHealth checking has ejected every origin. Confirm the health_check block expects a response the origin actually returns — a wrong resp_code ejects a healthy server.
Wrong site servedThe routing chain matched the wrong rulehttp_chain is first-match-wins. A catch-all placed early makes every rule below it unreachable — move it last.

Performance and monitoring

/proc/vet_waf/perfstat is the live counter set: requests, responses, cache hits and misses, and errors. Watch it while you generate load rather than sampling it once.

bash 
watch -n1 cat /proc/vet_waf/perfstat

# Frang decisions as they happen
sudo dmesg -w | grep -i frang
  • A low cache hit ratio means the origin is absorbing traffic that Vet-WAF could have served from RAM. Enable cache 2; with cache_fulfill * *; — on an edge node this is the difference between surviving a flood and forwarding it.
  • Connections pile up under attack — lower keepalive_timeout so idle slots are reclaimed quickly and stay available for real users.
  • The origin is overwhelmed while Vet-WAF is idle — raise conns_n= on the server line so connection churn is absorbed at the edge instead of being passed through.

Still stuck

Open an issue on GitHub or email trong20843@gmail.com. Include the output of uname -r, the relevant part of your configuration, and the last 50 lines of dmesg — that last one usually contains the answer already.
