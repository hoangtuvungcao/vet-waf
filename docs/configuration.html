Configuration

Everything Vet-WAF does is driven by one file. This page covers its syntax and every block you are likely to need, in the order they appear.

File and syntax

Vet-WAF reads etc/vet_waf.conf from the source tree by default; override the path with the TFW_CFG_PATH environment variable. A packaged install normally keeps it at /etc/vet_waf/vet_waf.conf.

  • One directive per line, always terminated by a semicolon ;.
  • # starts a comment and runs to the end of the line.
  • Braces { } group directives into a section, such as frang_limits or srv_group.
  • Sizes are in bytes and durations in seconds unless a directive says otherwise.
  • #!include /path/to/file.conf splices in another file — useful for large bot-blocking rule sets.

Order matters in two places: a health_check block must be defined before the srv_group that names it, and rules in http_chain are evaluated top to bottom with the first match winning — so a catch-all placed early makes everything after it unreachable.

Listeners and TLS

Vet-WAF terminates TLS inside the kernel, so HTTPS is the fast path rather than a slow one. Prefer it in production.

vet_waf.conf 
listen 80;
listen 443 proto=h2,https;

# A global certificate applies to the implicit default vhost only.
tls_certificate     /etc/vet_waf/tls/server.crt;
tls_certificate_key /etc/vet_waf/tls/server.key;

A global tls_certificate and an explicitly named vhost are mutually exclusive — Vet-WAF rejects the config at startup. A named vhost serves its own certificate over SNI, so move both tls_certificate lines inside the vhost block whenever you name one.

Backends and failover

A srv_group is a pool of origin servers. List more than one server line and Vet-WAF load-balances across them, taking any that stops responding out of rotation automatically.

vet_waf.conf 
health_check origin_hc {
    request     "GET / HTTP/1.1\r\nHost: localhost\r\n\r\n";
    request_url "/";
    resp_code   200;
    timeout     5;
}

srv_group primary {
    server 85.117.239.3:80 conns_n=64;
    server 10.0.0.9:80     conns_n=32;   # standby origin

    sched ratio static;
    server_queue_size      1000;
    server_forward_timeout   60;
    server_forward_retries    5;
    server_connect_retries   10;
    health origin_hc;
}
DirectiveMeaning
conns_n=Pooled persistent connections to that origin. Pooling matters under attack: Vet-WAF absorbs the connection churn so the origin sees a small, steady set of long-lived connections.
schedratio static is weighted round-robin. Use hash instead when a given client must keep landing on the same origin.
server_queue_sizeHow many requests may queue before Vet-WAF sheds load. A bounded queue is what stops a slow origin from becoming an out-of-memory event on the proxy.
healthActively polls the origin and pulls it out of rotation the moment it answers incorrectly, instead of waiting for user requests to fail.

The name given to health is not validated when the config is parsed. If it matches no health_check block, Vet-WAF hits a BUG_ON and panics the kernel at startup. Keep the two names identical, and keep the health_check block above the srv_group.

Virtual hosts and routing

A vhost says how to serve a site; http_chain says which requests go to it. The chain is evaluated top to bottom and the first match wins.

vet_waf.conf 
vhost firewall.hidev.dev {
    proxy_pass primary;

    # Preserve the public hostname for the origin application.
    req_hdr_set Host firewall.hidev.dev;

    # Tell the app the original request was HTTPS, so it builds
    # correct absolute URLs when Vet-WAF terminates TLS.
    req_hdr_set X-Forwarded-Proto https;

    # Never leak backend software versions — fingerprinting is
    # step one of targeting a known CVE.
    resp_hdr_set Server "Vet-WAF";
}

http_chain {
    #!include /etc/vet_waf/ua_block_rules.conf

    host == "firewall.hidev.dev" -> firewall.hidev.dev;
    host == "*.hidev.dev"        -> firewall.hidev.dev;

    # Anything addressed to a hostname we do not serve is hostile
    # or misdirected — typically a scanner hitting the bare IP.
    -> block;
}

A chain rule matches on one of six fields, with == or != and an optional * wildcard at either end of the value:

FieldMatches
hostThe request Host header or :authority
uriThe request path and query
hdrAn arbitrary header, e.g. hdr "Referer" == "*evil.com"
methodThe HTTP method
cookieA named cookie value
markThe netfilter mark on the packet

End the chain with -> block; rather than a catch-all vhost. Requests arriving for a hostname you do not serve are almost always scanners probing your bare IP, and answering them tells the attacker there is something here worth attacking.

Cache and block actions

The cache is also a DDoS defence: a cache hit is served from kernel RAM and never reaches your application, which is what lets one edge node absorb a large flood.

vet_waf.conf 
cache 2;                # 2 = sharded cache; 0 disables
cache_fulfill * *;      # cache every cacheable response
cache_methods GET HEAD;
cache_ttl 3600;

keepalive_timeout 30;   # reclaim idle slots fast under attack

block_action attack drop;
block_action error  reply;

block_action attack drop sends no reply packet at all. That costs the attacker a full timeout, costs you nothing, and denies them the feedback they need to tune their tooling. block_action error reply keeps answering ordinary client mistakes politely, so real but buggy clients can still see what went wrong.

Applying changes

A reload pushes the new configuration into the running kernel without dropping established connections. If the new config is rejected, the previous one stays in force — the proxy does not go down because of a typo.

bash 
sudo ./scripts/vet_waf.sh --reload      # from the source tree
sudo systemctl reload vet-waf          # packaged install

# The parser reports the offending directive and line here:
sudo dmesg | tail -30

There is no offline syntax checker. Reload on a staging node first and read dmesg — the parser names the exact directive it could not accept.
