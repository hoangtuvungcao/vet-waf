One engine, the whole frontend

Vet-WAF fuses a web accelerator and a multi-layer firewall into a single kernel-space core — no context switches, no user-space copy overhead.

Web Application Firewall

Inspect and filter HTTP/HTTPS at wire speed. Block injections, bad bots, and abusive clients with rule-based and rate-limiting policies (Frang).

HTTPS Load Balancer

Terminate TLS and balance traffic across upstreams with hash, ratio, and predictive schedulers — all inside the kernel data path.

Web Accelerator

A built-in, RAM-resident HTTP cache serves hot content in microseconds and shields origins from load spikes.

DDoS Mitigation

Absorb volumetric and application-layer floods early in the stack, with seamless integration into Linux iptables / nftables.

Kernel-native TLS

Vet-WAF TLS runs the handshake in-kernel — 40–80% faster than Nginx/OpenSSL, with optional constant-time crypto.

Observability

Structured access logging to ClickHouse, live perfstat via procfs, and APM-grade latency percentiles out of the box.

Defense in depth, from L3 to L7

Vet-WAF blocks attacks at the earliest possible point in the stack. The Frang module enforces rate and structural limits per client before a request ever reaches your origin.

Rate & connection limits

Per-client caps on request rate/burst, TCP connection rate/burst, and concurrent connections stop floods and slow-loris attacks cold.

Structural request validation

Bound header count, header length, body length and URI length; restrict HTTP methods and allowed character sets to shrink the attack surface.

JavaScript challenge

A sticky-cookie JS challenge separates real browsers from bots without a third-party captcha — fully self-hosted in the kernel.

Early drop & blocklists

Malicious clients are dropped (not just refused), and IP/JA5 fingerprint rules integrate with iptables/nftables for volumetric defense.

Anti-DDoS tip: the shipped config is secure-by-default. Tune the Frang limits to your real traffic — start strict, then relax only what your legitimate clients need.

Built for the fast path

Quick start

Build from source against a Vet-WAF-patched Linux 6.12.12 kernel, then start the service.

bash 
# 1. Clone
git clone https://github.com/hoangtuvungcao/vet-waf.git
cd vet-waf

# 2. Build the kernel modules and user-space tools
make

# 3. Load and start Vet-WAF (reads /etc/vet_waf/vet_waf.conf)
sudo ./scripts/vet_waf.sh --start

# 4. Check runtime state
cat /proc/vet_waf/perfstat
sudo sysctl net.vet_waf.state

A minimal config lives in etc/vet_waf.conf. The systemd unit is vet-waf.service. Vet-WAF needs the patched kernel from linux-6.12.12.patch — see the deploy guide below.

Deploy guide: reverse-proxy in front of a backend

Put Vet-WAF on your edge server and proxy protected traffic to your origin. Follow the steps in order — the kernel step is mandatory.

1

Install the patched kernel

Vet-WAF is a kernel module and requires the patched Linux 6.12.12. Build it with make bindeb-pkg LOCALVERSION=-tfw, or use make modules_install && make install. Reboot into the new kernel before continuing.

2

Point Vet-WAF at your backend

In /etc/vet_waf/vet_waf.conf, set server <backend-ip>:80; inside the srv_group. The shipped config uses https://example.com/ as a placeholder — replace it with your origin.

3

Free the ports & start the service

Stop any existing proxy holding :80/:443, then systemctl enable --now vet-waf. Verify with curl -I http://your-edge-ip/ and cat /proc/vet_waf/perfstat.

Pitfalls we hit (so you don't have to)

  • Stock kernels won't load the module. A default Ubuntu 5.15 kernel is missing the Vet-WAF patch — you must build and boot 6.12.12-tfw first.
  • bindeb-pkg needs debhelper. If packaging fails with Unmet build dependencies: debhelper-compat, install debhelper or fall back to make modules_install && make install.
  • Port already in use. Another WAF/proxy on :80 blocks startup — stop and disable it before enabling vet-waf.
  • Disable module signing. Turn off MODULE_SIG, SYSTEM_TRUSTED_KEYS and DEBUG_INFO_BTF in the kernel config, or the out-of-tree build fails.

Simple, secure-by-default config

A newcomer-friendly starting point: one listener, one backend, hardened Frang limits. Everything else is optional.

vet_waf.conf 
# --- Listener -------------------------------------------------
listen 80;

# --- Anti-DDoS / WAF limits (per client) ---------------------
frang_limits {
    request_rate         100;   # requests/sec
    request_burst         30;
    tcp_connection_rate   50;
    concurrent_tcp_connections 100;
    http_methods          get head post;
    http_header_cnt       50;
    http_hdr_len        4096;
    http_body_len    16777216;   # 16 MB
    http_strict_host_checking true;
}
block_action attack   drop;   # drop attackers silently
block_action error    reply;  # reply on client errors

# --- Backend (replace with your origin) ----------------------
srv_group primary { server https://example.com; }

vhost default { proxy_pass primary; }
http_chain    { -> default; }

Full reference lives in the project wiki. Start strict and relax only what your real clients need.
